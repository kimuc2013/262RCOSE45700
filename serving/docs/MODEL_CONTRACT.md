# 모델 담당자와 맞출 API 계약 초안

실제 FuriosaAI 런타임에서 확인한 규격이 아닙니다. 서빙 파트는 아래 규격으로 연결 어댑터와 계약 테스트를 준비했습니다. 경로나 응답 형식이 다르면 어댑터를 수정합니다.

| 기능 | 요청 | 응답 |
|---|---|---|
| 재작성 | `POST /v1/chat/completions`, model, messages, temperature=0, response_format=json_object | choices[0].message.content의 JSON 문자열 `{query, semester, target}` |
| 임베딩 | `POST /v1/embeddings`, model, input: 문자열 배열 | data: `[{index, embedding: 숫자 배열}]` |
| 리랭킹 | `POST /v1/rerank`, model, query, documents: 문자열 배열 | results: `[{index, relevance_score}]` |

리랭킹 경로는 `RERANK_PATH`로 변경 가능합니다. 후보마다 점수 하나, 원래 후보의 0부터 시작하는 index가 필요합니다. 현재는 모든 후보 점수를 반환하는 계약입니다. top-n 일부만 반환하는 서버라면 맞춰야 합니다. 임베딩도 입력 개수만큼 벡터가 있어야 합니다.

확인해야 할 사항:

- NPU 주소, AWS에서 접근할 네트워크 경로, 인증 방식
- 세 모델의 지원 여부, 고정 모델 ID와 버전, 임베딩 차원
- 리랭킹 경로와 응답 JSON, 점수의 방향과 범위
- JSON 출력 지원 여부, 재작성 결과에서 맥락 부족을 어떻게 표시할지
- 최대 입력 길이, 배치 크기, 동시 요청 한도와 타임아웃
- 임베딩의 query/document prefix 필요 여부. 현재 어댑터는 prefix를 임의로 추가하지 않음
- 같은 평가셋으로 정할 근거 판정 임계값, 재작성 품질, 후보 수

## 실제 엔드포인트 확인 결과 (2026-11-16, 모델 담당)

위 표의 임베딩과 리랭킹 규격을 실제 Furiosa 엔드포인트로 확인했습니다. EC2에서 순차 호출한 관측값이며 부하 시험이 아닙니다. 엔드포인트 주소는 공개 저장소에 적지 않습니다(팀 채널의 Furiosa RAG API 가이드 참고). 재작성(`/v1/chat/completions`)은 확인하지 않았습니다.

| 항목 | 임베딩 | 리랭킹 |
|---|---|---|
| 경로와 응답 형식 | `POST /v1/embeddings`, 위 표와 일치. `usage`도 반환 | `POST /v1/rerank`, 위 표와 일치. 모든 후보 점수를 내림차순으로 반환 |
| 모델 ID | `furiosa-ai/bge-m3` | `furiosa-ai/bge-reranker-v2-m3` |
| 주소 | 리랭킹과 **같은 호스트, 다른 포트** | 임베딩과 **같은 호스트, 다른 포트** |
| 인증 | 헤더 없이 200 | 헤더 없이 200 |
| 출력 | 1024차원, L2 norm 1.0, 같은 입력은 같은 벡터 | `relevance_score` 0~1, 클수록 관련 |
| 최대 입력 | `/v1/models`의 `max_model_len` 8192 | 8192 |
| prefix | 질의와 문서 모두 prefix 없이 사용 | 해당 없음 |

- **주소가 둘입니다.** 현재 `RemoteModels`는 `MODEL_BASE_URL` 하나에 `/v1/embeddings`와 `RERANK_PATH`를 붙이므로, 그대로는 두 모델을 함께 호출할 수 없습니다.
- **요청의 `model` 값은 무시됩니다.** 없는 모델명을 보내도 200과 `furiosa-ai/bge-m3` 응답이 옵니다. 모델이 바뀐 것을 알려면 응답의 `model` 필드를 확인해야 합니다. 현재 어댑터는 확인하지 않습니다.
- 배치: 한 요청 32개(`index.py` 기본값)와 64개 모두 200. 그보다 큰 배치와 동시 요청 한도는 확인하지 않았습니다.
- 색인: 실제 백필 스냅샷 `2026-11-12-2cc834ab`의 청크 308개를 `python -m academic_mcp.index`로 코드 수정 없이 색인했습니다. 약 20초, 벡터 payload 약 7MB(JSON). 문서 입력의 최대 길이는 1,983자였습니다.
- 지연(네트워크와 서버 대기 포함): 질의 임베딩 1건은 연결을 재사용하면 약 210ms, 호출마다 새 연결을 만드는 현재 `RemoteModels.post` 방식으로는 약 600ms였습니다. 후보 20개 리랭킹은 약 850ms였습니다.
- `load_vectors`는 308개 기준 호출당 약 130ms(JSON 디코딩)이며 캐시 미적중 검색마다 실행됩니다.

질의, 대화와 수집 문서는 데이터로 전달합니다. 문서의 지시를 따르지 않는다고 표시하지만 실제 인젝션 방어 평가는 별도로 해야 합니다. 모델 응답이 잘못됐거나 서버 연결에 실패하면 요청이 오류로 끝나며, 임의 모델이나 가짜 벡터로 대체하지 않습니다.
