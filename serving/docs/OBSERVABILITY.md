# 서빙 효율 측정과 비공개 백오피스

답변 모델보다 답변을 잘한다고 가정하지 않고, 공식 자료의 출처와 서버 운영 효율을 측정한다. 검색 캐시와 완성 답변 캐시는 효과가 다르다. 검색 캐시는 임베딩/리랭커 호출을 줄이지만 클라이언트의 답변 생성 토큰을 없애지 않는다. 완성 답변 캐시는 생성까지 생략하지만 MCP 클라이언트가 다시 문장을 작성하면 그 시간과 토큰은 별도다.

## 수집

`SERVING_METRICS_DB`를 설정하면 서버 도구 호출과 실제 온라인 API 작업을 별도 SQLite DB에 기록한다. Compose는 `/data/telemetry.sqlite3`를 사용한다. 설정하지 않으면 비활성이다. 기존 학사 DB와 캐시, 모델 및 백필 구현은 변경하지 않는다.

- 요청: 도구명, 상태, 서버 실행 시간, 캐시 적중, 진행 중 요청 합치기, 관측 가능한 검색 캐시, 응답 모드, 구조화 결과의 UTF-8 JSON 바이트 수. 바이트는 실제 MCP 전송량이나 토큰 수가 아니다.
- 물리 API 시도: 임베딩/리랭킹/생성 구분, 요청 모델, 호출 시간, HTTP 상태/오류 종류, 공급자가 반환한 usage. 복구 호출과 실패, 호출자 시간 초과 후 끝난 작업도 작업 기준으로 한 번씩 센다.
- 토큰: 입력/출력/총량/공급자 prompt-cache 토큰을 실제 제공된 경우에만 합산한다. 없는 usage는 미확인이며 0이 아니다. 외부 ChatGPT 등의 토큰은 계측하지 않는다. API가 토큰을 보고해도 청구 비용을 안다는 뜻은 아니다.
- 질문, 대화, 답변 본문, 문서, URL, 인증키, 사용자 IP와 안정적인 사용자 식별자는 저장하지 않는다. 임의 추적 ID로 요청과 해당 작업을 연결한다.

도구 경계에서만 요청을 세므로 내부 검색을 중복 요청으로 집계하지 않는다. API는 호출자 응답의 model_calls를 합산하지 않고 HTTP 경계에서 센다. 동시 요청 합치기에 의해 공유된 작업을 여러 번 세지 않는다. 모델 모듈은 변경하지 않고 서빙에서 기존 pooled client의 post 경계만 감싼다. legacy RemoteModels 경로의 내부 HTTP 호출은 계측하지 않으므로 API 수가 해당 모드의 총 사용량이라고 주장하지 않는다.

기록은 최대4096개 큐와 별도 writer 스레드를 사용한다. 최대7일/100,000이벤트를 보존한다. 큐가 가득 차거나 DB 쓰기에 실패하면 사용자 요청을 막지 않고 유실/실패를 센다. 손실이 있는 구간은 완전한 집계가 아니다. 종료 시 최대3초 flush를 시도하며 강제 종료의 미기록 데이터는 완벽히 검출할 수 없다. API 이벤트는 끝날 때 기록하므로 진행 중 작업과 아직 끝나지 않은 실패는 즉시 보이지 않을 수 있다.

## 내보내기

운영 EC2에서 읽기 전용으로 실행한다. 공개 MCP에는 관리자 조회 도구나 대시보드 URL을 추가하지 않았다.

```bash
sudo docker exec ku-academic-mcp-mcp-1 academic-metrics \
  --db /data/telemetry.sqlite3 --hours 24 \
  --html /tmp/serving-metrics.html --json /tmp/serving-metrics.json
```

필요하면 `docker cp`와 SSH로 산출물만 내려받는다. DB를 직접 내보낼 때는 WAL 파일을 단순 복사하지 말고 SQLite backup을 사용한다. 생성된 HTML은 외부 리소스 없이 열리는 정적 백오피스다. 내보낸 시각의 스냅샷이며 실시간 화면이 아니다. HTML의 선택 상자로 일반/통제실험/전체를 구분한다. 서버 기간은 UTC timestamp, 화면은 KST다. 공개 게시하지 않는다.

통제 실험 클라이언트는 `X-KU-Experiment: cache-benchmark-v1`을 보낸다. 표식 없는 요청은 일반으로 집계되지만 실제 학생 사용을 보증하지 않는다. 클라이언트가 스스로 보내는 분류일 뿐 인증이나 권한 검사가 아니다. 과거 일반 호출로 실행한 smoke를 소급해서 자연 트래픽으로 재해석하지 않는다.

## 핵심 지표와 분모

1. 검색 캐시 적중률 = 검색 도구에서 cache_hit인 호출 / 검색 도구 전체 호출.
2. 완성 답변 캐시 적중률 = 답변 도구에서 cache_hit인 호출 / 답변 도구 전체 호출.
3. 합치기는 cache_hit와 별도로 표시한다. 캐시 또는 공유의 합집합도 제공한다. 실패와 시간 초과는 전체 호출 분모에 남긴다.
4. 답변 도구 내부의 검색 캐시는 실제 관측된 true/false만 표시한다. 완성 캐시 적중과 공유 호출은 검색을 새로 실행하지 않아 null이다. 전체 검색 적중률과 섞지 않는다.
5. answered p50/p95와 전체 반환 p50/p95를 분리한다. 2초 answered 비율은 can_answer=true이면서 answered이고 서버2초 이내인 호출 / 전체 답변 호출이다. 근거 부족, 오류와 시간 초과를 성공으로 세지 않는다. answered는 사실 검증 결과가 아니다.
6. usage 제공 횟수를 함께 표시한다. API 오류와 복구 작업의 토큰도 응답에 있으면 포함한다. 캐시에서 과거 usage를 가져와 새 소비로 더하지 않는다.

## 비교 실험 원칙

일반 웹검색/LLM과의 토큰 절감률은 그쪽의 실제 도구 호출 및 모델 usage까지 같은 모델, 프롬프트, 질문과 출력 품질 조건으로 수집해야 말할 수 있다. 지금 수집하는 것은 우리 서버의 실제 호출/usage와 캐시 효과이며 비교 기준선이 없으면 절감률/금액을 표시하지 않는다. ChatGPT 구독 화면의 답변만으로 토큰 사용량을 알 수 없다.

통제 실험은 최초 호출과 같은 질문의 다른 대화 반복을 분리하고, cold 여부를 실제 cache_hit로 확인한다. 반복되도록 만든 실험의 적중률을 운영 자연 적중률로 쓰지 않는다. 속도는 검색만이 아니라 최종 답변 완료까지 외부 왕복으로 별도 측정한다. 토큰이 줄어도 답변 품질이 나빠졌다면 우위라고 주장하지 않는다. 단일 학생 질문보다 학사 상담/행정 도구처럼 공통 질문이 반복되는 사용 패턴에서 이점을 검증한다.
