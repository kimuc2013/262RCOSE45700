# 서빙 효율 측정과 비공개 백오피스

답변 모델보다 답변을 잘한다고 가정하지 않고, 공식 자료의 출처와 서버 운영 효율을 측정한다. 검색 캐시와 완성 답변 캐시는 효과가 다르다. 검색 캐시는 임베딩/리랭커 호출을 줄이지만 클라이언트의 답변 생성 토큰을 없애지 않는다. 완성 답변 캐시는 생성까지 생략하지만 MCP 클라이언트가 다시 문장을 작성하면 그 시간과 토큰은 별도다.

## 수집

`SERVING_METRICS_DB`를 설정하면 서버 도구 호출과 실제 온라인 API 작업을 별도 SQLite DB에 기록한다. Compose는 `/data/telemetry.sqlite3`를 사용한다. 설정하지 않으면 비활성이다. 기존 학사 DB와 캐시, 모델 및 백필 구현은 변경하지 않는다.

- 요청: 도구명, 상태, 서버 실행 시간, 캐시 적중, 진행 중 요청 합치기, 관측 가능한 검색 캐시, 응답 모드, 구조화 결과의 UTF-8 JSON 바이트 수. 바이트는 실제 MCP 전송량이나 토큰 수가 아니다.
- 물리 API 시도: 임베딩/리랭킹/생성 구분, 요청 모델, 호출 시간, HTTP 상태/오류 종류, 공급자가 반환한 usage. 복구 호출과 실패, 호출자 시간 초과 후 끝난 작업도 작업 기준으로 한 번씩 센다.
- 토큰: 입력/출력/총량/공급자 prompt-cache 토큰을 실제 제공된 경우에만 합산한다. 없는 usage는 미확인이며 0이 아니다. 외부 ChatGPT 등의 토큰은 계측하지 않는다. API가 토큰을 보고해도 청구 비용을 안다는 뜻은 아니다.
- 질문, 대화, 답변 본문, 문서, URL, 인증키, 사용자 IP와 안정적인 사용자 식별자는 저장하지 않는다. 임의 추적 ID로 요청과 해당 작업을 연결한다.

도구 경계에서만 요청을 세므로 내부 검색을 중복 요청으로 집계하지 않는다. API는 호출자 응답의 model_calls를 합산하지 않고 HTTP 경계에서 센다. 동시 요청 합치기에 의해 공유된 작업을 여러 번 세지 않는다. 모델 모듈은 변경하지 않고 서빙에서 기존 pooled client의 post 경계만 감싼다. legacy RemoteModels 경로의 내부 HTTP 호출은 계측하지 않으므로 API 수가 해당 모드의 총 사용량이라고 주장하지 않는다.

기록은 최대4096개 큐와 별도 writer 스레드를 사용한다. 최대7일/100,000이벤트를 보존한다. 큐가 가득 차거나 DB 쓰기에 실패하면 사용자 요청을 막지 않고 유실/실패를 센다. 손실이 있는 구간은 완전한 집계가 아니다. 종료 시 최대3초 flush를 시도하며 강제 종료의 미기록 데이터는 완벽히 검출할 수 없다. API 이벤트는 끝날 때 기록하므로 진행 중 작업과 아직 끝나지 않은 실패는 즉시 보이지 않을 수 있다.

## 내보내기

운영 EC2에서 읽기 전용으로 실행한다. 공개 MCP에는 관리자 조회 도구를 추가하지 않는다. 실시간 HTTP 지표 API는 아래처럼 소유자 인증으로 별도 보호한다.

```bash
sudo docker exec ku-academic-mcp-mcp-1 academic-metrics \
  --db /data/telemetry.sqlite3 --hours 24 \
  --html /tmp/serving-metrics.html --json /tmp/serving-metrics.json
```

필요하면 `docker cp`와 SSH로 산출물만 내려받는다. DB를 직접 내보낼 때는 WAL 파일을 단순 복사하지 말고 SQLite backup을 사용한다. 생성된 HTML은 외부 리소스 없이 열리는 정적 백오피스다. 내보낸 시각의 스냅샷이며 실시간 화면이 아니다. HTML의 선택 상자로 일반/통제실험/전체를 구분한다. 서버 기간은 UTC timestamp, 화면은 KST다. 공개 게시하지 않는다.

통제 실험 클라이언트는 `X-KU-Experiment: cache-benchmark-v1`을 보낸다. 표식 없는 요청은 일반으로 집계되지만 실제 학생 사용을 보증하지 않는다. 클라이언트가 스스로 보내는 분류일 뿐 인증이나 권한 검사가 아니다. 과거 일반 호출로 실행한 smoke를 소급해서 자연 트래픽으로 재해석하지 않는다.

## 핵심 지표와 분모

1. 검색 캐시 적중률 = 검색 도구에서 cache_hit인 호출 / 검색 도구 전체 호출.
2. 완성 답변 캐시 적중률 = 답변 도구에서 cache_hit인 호출 / 답변 도구 전체 호출.
3. 합치기는 cache_hit와 별도로 표시한다. 캐시 또는 공유의 합집합도 제공한다. 실패와 시간 초과는 전체 호출 분모에 남긴다.
4. 답변 도구 내부의 검색 캐시는 실제 관측된 true/false만 표시한다. 완성 캐시 적중과 공유 호출은 검색을 새로 실행하지 않아 null이다. 전체 검색 적중률과 섞지 않는다.
5. answered p50/p95와 전체 반환 p50/p95를 분리한다. 2초 answered 비율은 can_answer=true이면서 answered이고 서버2초 이내인 호출 / 전체 답변 호출이다. 근거 부족, 오류와 시간 초과를 성공으로 세지 않는다. answered는 사실 검증 결과가 아니다.
6. usage 제공 횟수를 함께 표시한다. API 오류와 복구 작업의 토큰도 응답에 있으면 포함한다. 캐시에서 과거 usage를 가져와 새 소비로 더하지 않는다.

## 비교 실험 원칙

일반 웹검색/LLM과의 토큰 절감률은 그쪽의 실제 도구 호출 및 모델 usage까지 같은 모델, 프롬프트, 질문과 출력 품질 조건으로 수집해야 말할 수 있다. 지금 수집하는 것은 우리 서버의 실제 호출/usage와 캐시 효과이며 비교 기준선이 없으면 절감률/금액을 표시하지 않는다. ChatGPT 구독 화면의 답변만으로 토큰 사용량을 알 수 없다.

통제 실험은 최초 호출과 같은 질문의 다른 대화 반복을 분리하고, cold 여부를 실제 cache_hit로 확인한다. 반복되도록 만든 실험의 적중률을 운영 자연 적중률로 쓰지 않는다. 속도는 검색만이 아니라 최종 답변 완료까지 외부 왕복으로 별도 측정한다. 토큰이 줄어도 답변 품질이 나빠졌다면 우위라고 주장하지 않는다. 단일 학생 질문보다 학사 상담/행정 도구처럼 공통 질문이 반복되는 사용 패턴에서 이점을 검증한다.


## 실시간 화면

`/ops`는 지표가 없는 화면 껍데기다. `/ops/api/metrics?hours=1`은 기존 `MCP_OWNER_TOKEN` Bearer 인증만 허용한다. 팀 공유 키와 무인증은401이다. 토큰을 URL에 넣지 않는다. 공개 화면에서 입력한 키는 탭 메모리에만 유지하며 local/sessionStorage, 쿠키에 저장하지 않는다. 서버 및 브라우저 응답은 no-store이고 외부 차트 라이브러리/CDN은 쓰지 않는다.

인증 경계는 기존 Caddy다. owner 매칭 후에만 사설 backend에 X-KU-Metrics-Access: owner 표식을 설정한다. MCP/화면 경로는 이 표식을 제거하여 클라이언트의 위조 헤더를 전달하지 않는다. backend는127.0.0.1에만 포트를 노출한 기존 Docker network 내부 서비스다. 표식 자체는 별도 비밀 토큰이 아니므로 backend를 인터넷에 직접 노출하면 안 된다.

화면은5초 간격으로 조회한다. 최근15분/1시간/24시간과 일반/통제실험/전체를 구분하며,60구간 차트에 요청량/실패, 캐시/공유율, 전체 서버p50/p95, 모델 API 호출과 보고된 생성 토큰을 표시한다. API도5초 결과 캐시와 단일 조회 잠금을 사용하고 DB 분석은 MCP 실행 슬롯과 별도의 worker에서 한다. 시간 구간은 세 종류만 허용한다. 아직 DB가 없으면503, 연결 실패면 마지막 수신 시각과 오래된 상태를 표시하며 정적 샘플로 바꾸지 않는다. API 이벤트가 끝나고 비동기 기록이 반영된 뒤 보이므로 지연은 보통 수 초이고 엄격한 실시간 SLA는 아니다.

키를 브라우저에 입력하지 않으려면 로컬 브리지를 실행한다.

```bash
# MCP_URL과 MCP_OWNER_TOKEN(또는 기존 MCP_DEMO_TOKEN)은 비공개 환경에서 설정
academic-dashboard --port 18711
```

브리지는127.0.0.1에만 bind하며 서버로 가는 owner 키를 Python 프로세스에서 보관한다. 브라우저에는 키를 넘기지 않는다. Host/Origin 검증, 조회 시간 범위 제한, 동시 fetch 제한과 고정 HTTPS upstream을 사용한다. 로컬/공개 화면 모두 지표 원본을 수정하지 않는다. 지표를 조회하는 요청은 학사 도구 호출 통계에 포함하지 않는다. 정적 HTML 내보내기도 계속 사용할 수 있다.

### 도구 응답 공통 지표 (schema 2)

`search_academic_info`, `answer_academic_question`은 `metrics`에 동일한
호출 수와 시간 필드를 반환한다.

- `model_calls`: 이 요청이 시작한 서버 모델 호출 합계.
  `embedding_calls + rerank_calls + generation_calls + rewrite_calls`와 같다.
  온라인 HTTP 시도 기준이며 연결 복구와 생성 형식 보정 시도도 포함한다.
- `latency_ms`, `server_elapsed_ms`: 같은 서버 내부 경과 시간(ms)의 호환 별칭.
  큐 대기를 포함하고 클라이언트 LLM 생성과 네트워크 왕복은 제외한다.
- 정확 일치 응답 캐시는 각 호출 수가 0이다. 의미 캐시는 임베딩을 사용할 수 있다.
  원문 직접 답변도 검색을 했다면 임베딩/리랭킹 호출 수가 포함된다.
- `coalesced=true`이면 자기 호출 수는 0이다. 공유한 작업량은
  `shared_model_calls`, `shared_model_calls_by_stage`로 표시한다.
  요청별 총량을 합산할 때 공유 작업을 다시 더하면 안 된다.
- 답변 시간 초과는 실행 중인 worker의 최종 호출 수를 확정할 수 없어
  `model_calls_complete=false`와 응답 시점까지 시작한 호출 수를 반환한다.
  `model_calls_observed=true`는 그 시점의 실측값이며 최종 총량은 아니다.
  `timeout_stage`, `retrieval_complete`로 지연 구간을 구분한다. 지연 완료/실패를
  포함한 최종 물리 API 사용량은 운영 계측 이벤트로 확인한다.
- `metrics_schema_version=2`. 과거 응답에서 읽은 호출 수를 캐시 재사용 시
  재계상하지 않는다. 이 수치는 Claude Desktop 자체의 모델 호출 수가 아니다.


### 캐시 재사용 진단

- `semantic_cache_reason`: 응답/검색 순위 적중, 의미 적중, `signature_missing`,
  `no_compatible_candidate`, `below_threshold`, `ambiguous_sources`, 비활성 사유.
  질문, 문서 본문, 조건 원문은 운영 계측에 저장하지 않는다.
- `semantic_candidate_count`, `semantic_best_similarity`: 같은 보호 조건 안의
  후보 수와 최고 유사도. 다른 대상/학기/숫자 조건으로 후보를 넓히지 않는다.
- `embedding_cache_hit`: 온라인 질문 벡터 조회 여부. 질문과 임베딩 모델,
  모델 버전 및 데이터 버전으로 격리한다. 실패한 벡터는 저장하지 않는다.
  임베딩만 재사용해도 리랭킹은 새로 수행할 수 있다.
- 검색 순위 캐시는 명시적인 요청 존댓말만 정규화한다. 날짜, 숫자, 학점,
  부정과 대상은 삭제하지 않는다. 전체 응답과 의미 캐시의 학기/대상
  격리는 유지한다. 입력 질의만 사용하는 검색 순위는 기존 후보 폭 재사용을 유지한다.
- 대시보드의 캐시 진단은 필드가 추가된 이후 관측분만 보여준다. 임베딩
  적중률 분모는 임베딩 캐시 조회를 관측한 요청이며 전체 요청이 아니다.


### 배포 버전 확인

두 도구의 `metrics`에는 캐시 적중과 `answer_timeout` 응답에도 다음 필드가 있다.

- `server_version`: 현재 실행 이미지의 Git 커밋 앞 12자리. 팀원 간 먼저 비교할 값.
- `release_sha`: 전체 40자리 커밋. Docker 빌드 시 이미지 파일과 OCI label에 고정한다.
  롤백 시에도 이전 이미지가 자신의 원래 커밋을 반환한다.
- `server_instance`: 현재 서버 프로세스의 익명 실행 ID. 재시작하면 달라진다.
- `metrics_schema_version`: 지표 계약 버전(현재 2). Git 배포 버전과 구분한다.
- `request_budget_ms`: 해당 요청에 적용한 서버 시간 예산. 답변 도구의 기본값은 1850ms.
- `timeout_stage`: 시간 초과 응답에서 지연된 단계(기존 최상위 필드도 유지).

로컬 개발은 `local`, 이미지 빌드 커밋이 누락되면 `unversioned`와 null SHA로
표시한다. 캐시에 저장된 이전 배포의 값을 재사용하지 않고 응답 시 현재 버전을
붙인다. 동일 버전인지 확인할 때는 버전, request_id, timeout_stage, 시간 예산,
단계별 호출 수를 함께 비교한다. 버전 표시는 시간 초과가 해소되었다는 뜻이 아니다.

## 모델 무호출 응답률

운영 API와 shadcn 차트에 `model_free_response_rate`를 추가했다. 답변 도구의 분모는 **answered이고 can_answer=true인 완료 응답**, 분자는 그 중 완료된 계수에서 **공유 작업까지 실제 모델 호출 0회**가 확인된 응답이다. 보류, 오류, 취소, timeout은 완료 답변 분모에 포함하지 않는다. 다른 요청의 모델 작업을 공유한 caller는 자기 호출 0회여도 분자에 들어가지 않는다. 완료는 사실 정확성 검증을 뜻하지 않는다.

이전 이벤트에서 계수가 빠진 경우는 무호출로 추정하지 않고 `model_free_measurement_coverage`로 계측 커버리지를 함께 보여준다. `model_free_reasons`는 응답 캐시, 검증된 별칭, 공식 항목 직접 조회, 구조화 일정, 모델 없는 작업 공유 등을 중복 없이 분류한다. 검색/일정 도구의 정상 응답은 found/evidence_available이다. 무호출 시계열은 답변 도구만 집계하며 분모가 없는 구간은 null이다. 정규화 캐시 히트율(전체 요청 분모)과 무호출 응답률(완료 응답 분모)은 직접 같은 비율로 비교하면 안 된다.

통제 실험 클라이언트는 `x-ku-experiment: cache-benchmark-v1`을 사용해 일반 호출과 구분한다. 이 표식은 집계 라벨이며 인증 권한은 부여하지 않는다. 대시보드에서 통제 실험 필터를 선택할 수 있다. 질문/원문/인증키를 새 telemetry 필드에 기록하지 않는다.

진행 중 검색/임베딩 일부만 공유했고 공유 작업의 최종 물리 호출 수가 전달되지 않는 경우는 `shared_model_work_unknown=true`와 `model_free_response=null`로 보수적으로 처리한다. SQLite 조회만 공유했을 가능성도 있어 실패나 모델 사용으로 단정하지 않고 계측 불명으로 남긴다.

owner 지표의 최상위 `server`는 현재 보고서를 만든 서버의 배포SHA/익명인스턴스다. 과거를 포함한 집계 전체가 같은 버전이라는 뜻은 아니다. footer에는 현재 서빙 버전을 표시한다. 요청 지표에 HTTP 단계/바이트/연결 수와 선택적 최종 캐시 저장 상태를 콘텐츠 없이 저장한다.

### 데이터 버전 기반 캐시 (2026-11-27)

`build_service()`는 `SERVING_REVISION_CACHE=true`를 기본으로 사용한다. 일반 규정 질문의 검색 응답, 검증된 검색 결과, 질문 벡터, 정상 최종 답변은 시간 TTL 대신 현재 스냅샷 및 처리 정책 버전 동안 재사용한다. 오늘, 이번 학기, 일정, 신청일, 마감 등 시간 표현이 있으면 기존 TTL과 날짜 구분을 유지한다. 생성 답변 자체에 상대 시간 표현이 포함돼도 날짜를 넘겨 재사용하지 않는다. 캐시 조회 때 수집일 기준 최신성 경고는 다시 계산한다.

이는 저장 공간 무제한 보장이 아니다. 약 1,000개 항목의 기존 용량 제한, 데이터 스냅샷 및 색인 교체, 모델 프로필과 정책 변경에 따른 무효화는 유지한다. 전체 검색은 새 문서 추가로 순위가 바뀔 수 있으므로 데이터 스냅샷이 바뀌면 기존 전체 무효화를 유지한다. 외부 사이트 변경은 새 수집 데이터가 적재돼야 반영된다. 긴 보관이 원문 재수집을 대신하지 않는다. `SERVING_REVISION_CACHE=false`로 기존 TTL 방식에 복귀할 수 있다. 직접 `AcademicService`를 구성하는 호출자는 `revision_cache=True`로 활성화한다.

`retrieval_cache_kind=verified_intent`, `semantic_cache_reason=verified_intent_cache_hit`는 전체 질문 문법으로 동일 의도와 주제 슬롯을 검증해 검색 결과를 공유한 경우다. 새 임베딩 없이 재사용하며 검색 점수는 `cached_` 출처로 표시한다. 문법을 벗어난 질문은 기존 검색 또는 보수적인 의미 캐시로 넘어간다. 모델의 점수 임계값이 설정돼 있으면 검증 별칭 경로도 사용하지 않는다. 숫자, 학교와 학과, 부정, 대상 조건을 임의로 제거하거나 유사도 임계값을 낮추지 않는다.

`cache_hit`는 완성된 도구 응답 캐시다. 새 질문 표현에서 `cache_hit=false`여도 `retrieval_cache_hit=true`, `model_calls=0`이면 검색 결과를 재사용한 모델 무호출이다. `cache_retention_policy=revision-static-v1`로 현재 정책을 확인한다. 질문 원문은 telemetry에 추가하지 않는다.
