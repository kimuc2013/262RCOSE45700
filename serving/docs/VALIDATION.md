# 로컬 검증 기록

## 2026-11-06 자동 배포 파이프라인 준비

GitHub Actions의 Python 3.12 테스트 및 Docker 빌드, main 전용 OIDC/SSM 배포 job을 추가했습니다. 로컬 전체 회귀 테스트는 60개 통과했습니다. 실제 로컬 MCP HTTP 서버에 새 smoke 검사를 호출했습니다. 배포 셸 테스트는 격리된 가짜 Docker로 새 이미지 적용, 기존 DB 보존, 빌드 실패 시 재시작 방지, MCP 검사 실패 시 이전 이미지 복구 및 실패 종료를 검증했습니다. SSM 원격 실패가 배포 성공으로 처리되지 않는지도 검사했습니다.

실제 AWS OIDC, SSM 등록과 EC2 배포는 미검증입니다. Docker를 모사한 복구 테스트는 실제 EC2 장애 복구 훈련이 아닙니다. 활성화 전제와 학교 계정의 IAM 제한은 DEPLOYMENT.md에 기록했습니다.

## 2026-11-06 실제 MCP HTTP 부하테스트

`python -m academic_mcp.load_test` 도구를 추가하고 격리된 샘플 DB와 별도 서버로 실행했습니다. 실제 네트워크와 독립 MCP 세션을 사용했습니다. 데이터는 일정 43건, 청크 9개이며 모델 API는 호출하지 않았습니다. 기존 개발 DB와 실행 중 서버는 변경하지 않았습니다.

1차는 동시성 1, 8, 32, 96에서 시나리오별 192건, 총 3,072건입니다. 2차는 동시성 8에서 시나리오별 2,000건, 총 8,000건입니다. 합계 11,072건 중 10,749건 정상 도구 응답, 323건 SERVER_BUSY이며 그 외 오류는 없었습니다. 정상 응답 수는 검색 정답률을 뜻하지 않습니다.

| 1차 동시성 | 총 요청 | 정상 응답 | SERVER_BUSY |
|---:|---:|---:|---:|
| 1 | 768 | 768 | 0 |
| 8 | 768 | 768 | 0 |
| 32 | 768 | 688 | 80 |
| 96 | 768 | 525 | 243 |

동시성 32의 서로 다른 질문에서 80건, 동시성 96의 네 시나리오 합계에서 243건이 제한됐습니다. 실행 4개, 대기 8개, 호출자 64개 및 별도 캐시 경로의 제한이 적용된 결과이며 모든 동시성에서 무오류를 달성했다는 뜻이 아닙니다. 거절을 줄이기 위해 한도를 무작정 늘리지 않았습니다.

| 2차 시나리오, 동시성 8 | 성공/요청 | 클라이언트 p95(ms) | 성공 처리량(req/s) | 캐시 적중 | 검색 작업 병합 |
|---|---:|---:|---:|---:|---:|
| 예열된 동일 질문 | 2000/2000 | 131.523 | 110.81 | 2000 | 0 |
| 캐시 없이 시작하는 동일 질문 | 2000/2000 | 81.796 | 193.89 | 1992 | 7 |
| 매번 다른 키 | 2000/2000 | 139.432 | 139.38 | 0 | 0 |
| 일정 조회 | 2000/2000 | 141.551 | 111.4 | 0 | 1406 |

독립 세션마다 응답 후 다음 요청을 보내는 closed-loop 방식이며 연결, 초기화, 예열 시간은 제외했습니다. cold_shared는 최초 묶음만 미적중이며 이후 캐시를 사용합니다. 전체 지연 분위수는 오류도 포함하므로 성공 p95와 성공률을 함께 봅니다. 거절 응답을 성공 처리량에 포함하지 않습니다.

클라이언트와 서버가 같은 macOS 개발 호스트에서 실행됐으며 다른 로컬 작업과 자원을 공유했습니다. 2차 후반에는 회귀 테스트도 같은 호스트에서 실행했습니다. 수치는 해당 실행의 관측값이며 통제된 전후 성능 비교, 장시간 안정성, 개별 유저 공정성, EC2 용량 또는 실제 모델 처리량의 근거가 아닙니다. CPU와 RSS는 이 도구에서 측정하지 않았습니다. 회귀 테스트는 여전히 56개 통과했습니다.

원시 결과: `load-test-20261106.json`, `load-test-20261106-longer.json`. 실행법은 README.md의 실제 MCP 부하테스트 절을 참고하세요.


## 2026-11-06 앞단 최적화와 다중 요청 검증

전체 회귀 테스트 56개 통과. 실제 로컬 Streamable HTTP 테스트 안에서 검색 20건을 동시에 호출하고, 캐시가 채워진 뒤 20건을 다시 호출했습니다. 모두 성공했고, 두 번째 묶음은 전부 `cache_fast_path=true`, 모델 호출 0회, 호출자별 request ID가 달랐습니다. 외부 모델과 AWS 부하 성능 측정은 아닙니다.

추가 검증:

- 검색 슬롯 1개가 막힌 상태에서도 기존 캐시를 조회하는 20개 호출이 검색 슬롯 없이 응답합니다.
- 동기 및 비동기 캐시 적중 경로에서 코퍼스 로딩 함수를 호출하면 실패하도록 검사했습니다.
- 대기 중 다른 생산자가 저장한 캐시를 실행 직전에 재확인하여 검색을 생략합니다.
- 최초 DB 조회가 막혀 있어도 추가 호출을 제한합니다. 검색과 일정에서 취소 후 한도가 반환됩니다.
- 최신 테이블 스냅샷의 JSON 디코딩을 재사용하고, 호출자 변조가 다른 호출자에게 전파되지 않으며, 다른 Store 인스턴스가 갱신한 revision을 반영합니다.
- 앞단 캐시 조회 중 데이터가 바뀌면 이전 결과를 반환하지 않습니다.
- 공유 캐시 조회의 최초 호출자를 취소해도 다른 호출자의 응답은 유지됩니다.

명령: `serving/.venv/bin/python -m pytest serving/tests -q`.
기존 Starlette 테스트 클라이언트의 httpx 사용에 대한 폐기 예정 경고 1개가 있습니다. 새로운 성능 목표나 지연 개선율을 주장하지 않습니다. 자세한 실행 구조와 단일 프로세스 한계는 ONLINE_CONTROLS.md를 참고하세요.


## 2026-10-29 MVP 화면 재현

`python -m academic_mcp.demo`로 127.0.0.1:8001에 개발용 화면을 실행하고 Docker MCP 서버(8000)를 실제 호출했습니다. 화면에서 일정 조회, 검색, 재질문 시 캐시 적중을 확인했습니다. 최종 답변 생성 모델과 AWS는 사용하지 않았습니다.

동시 호출 중 발견한 간헐적 SQLite 잠금은 WAL 모드와 이벤트 루프 밖의 revision 조회로 수정했습니다. revision 조회의 잠금 대기 역시 전체 요청 시간 예산에 포함합니다. 변경 후 실제 MCP로 캐시 미적중 질문을 20묶음, 묶음당 10건씩 보내 200건 성공, 오류 0건, 진행 중 작업 공유 180건을 확인했습니다. 이는 작은 샘플에 대한 로컬 재현이며 NPU 부하 성능 평가가 아닙니다.

회귀 테스트는 48개 통과했습니다. 새로운 검사는 DB 쓰기 중 revision 읽기, 데모 화면 제공과 입력 및 출처 검증입니다. 최종 브라우저 새로고침 시 Mac이 잠겨 화면을 다시 캡처하지 못했으며, 최종 코드의 응답은 실제 HTTP 호출로 검증했습니다.

사용한 MCP SDK는 `1.30.0`입니다. 웹의 최신 SDK 문서와 차이를 피하기 위해 설치된 v1 SDK 소스와 실제 프로토콜 호출로 검증했습니다. 일반 Python 테스트는 macOS Python 3.14에서 수행했고, 컨테이너는 Python 3.12에서 실행했습니다.

이 환경의 Compose 빌드는 경로 정규화에 따른 Docker Bake 경로 허용 오류가 있어 `docker build -t ku-academic-mcp:local .`로 빌드한 뒤 Compose로 실행했습니다. README도 검증된 순서로 작성했습니다.
