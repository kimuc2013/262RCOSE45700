# 온라인 서빙 제어

백필, SimHash, 모델 학습과 모델 서빙 구현은 이번 범위에서 제외했습니다. 모델 HTTP 연결부에는 남은 시간에 맞춘 타임아웃만 적용했습니다.

## 캐시 정확성

NFKC 유니코드 정규화, 소문자화, 연속 공백 정리, 한글 사이 띄어쓰기와 끝의 물음표/느낌표 차이를 정리합니다. 소수점, 숫자 사이 공백, 날짜 구분자, 신청/정정과 부정 표현은 지우지 않습니다. `3.5`와 `35`, `신청 가능`과 `신청 불가능`은 다른 키입니다.

대화 전체(순서와 역할 포함), top-k, 학기, 대상, 모델 설정, 임계값, 답변 지침 버전과 기준일을 키에 넣습니다. 재작성 전에 조회하며 서로 다른 대화가 같은 문장으로 재작성되어도 결과를 공유하지 않습니다.

캐시는 데이터 revision에 묶습니다. 저장 직전 확인은 쓰기 트랜잭션 안에서 수행합니다. 처리 도중 데이터가 바뀌면 이전 결과를 정상 응답으로 주지 않고 `DATA_CHANGED` 오류로 재시도를 요청합니다. TTL은 기존 300초이며 정책 버전을 바꿔 이전 개발판 캐시를 재사용하지 않습니다.

같은 모델 ID의 가중치나 설정을 교체하면 `SERVING_MODEL_REVISION`을 바꾸고 프로세스를 다시 시작하세요. 외부 가중치 변경은 자동으로 알 수 없습니다. 유사도 캐시와 어미/동의어 통합은 이번에 구현하지 않았습니다.

## 동일 요청 병합

같은 revision과 입력 맥락의 동시 요청은 재작성까지 포함해 한 작업으로 처리합니다. 다른 학기, 대상, 대화는 병합하지 않습니다. 호출자마다 독립된 응답 객체와 request ID를 받습니다.

`metrics.coalesced=true`는 진행 중 작업 공유를 뜻하며 영구 캐시 적중과 다릅니다. 병합 호출자의 `model_calls`는 0, 공유 작업의 호출 수는 `shared_model_calls`에 기록합니다.

한 호출자가 취소해도 다른 호출자가 기다리면 작업을 유지합니다. 모두 떠나면 대기 중 작업은 취소하고 실행 중 작업은 이후 단계와 캐시 쓰기를 중단합니다. 최초 요청의 마감시간을 공유하며 뒤늦게 합류한 요청이 시간을 연장하지 않습니다.

## 실행 한도와 시간 예산

| 환경변수 | 초기값 | 의미 |
|---|---:|---|
| `SERVING_MAX_RUNNING` | 4 | 검색 경로의 동시 실행 고유 작업 수 |
| `SERVING_MAX_QUEUED` | 8 | 추가 고유 작업 대기 수 |
| `SERVING_MAX_WAITERS` | 64 | 병합 호출자를 포함한 최대 대기 호출자 수 |
| `SERVING_REQUEST_TIMEOUT` | 10초 | 접수 후 전체 시간 예산 |
| `SERVING_QUEUE_TIMEOUT` | 1초 | 실행 슬롯 대기 상한 |

초기 운영 설정이며 실측 최적값이나 성능 목표가 아닙니다. 일정 조회는 별도 컨트롤러에서 동시 실행 2개를 허용하며 대기 수와 시간 설정은 검색 경로와 같습니다. 검색이 막혀도 일정 조회는 독립적으로 처리합니다.

2026-11-06부터 캐시 조회는 검색 실행 슬롯 앞의 별도 컨트롤러에서 수행합니다. 캐시 경로는 고유 조회 동시 실행 2개, 대기 8개로 제한하며 같은 키의 조회도 병합합니다. 시간과 호출자 한도는 검색 설정을 따릅니다. 적중하면 검색 슬롯을 사용하지 않고 최종 데이터 버전을 재확인한 뒤 반환합니다. 조회 경로 자체가 포화되면 오류를 반환하므로 무제한 우회는 아닙니다. 두 경로는 Python 기본 스레드 풀을 공유하므로 모든 검색 실행 수를 과도하게 늘리면 캐시 및 일정 경로도 지연될 수 있습니다.

검색 호출자 수는 최초 DB 조회 전부터 반환까지 `SERVING_MAX_WAITERS`로 제한합니다. 적중과 미적중 호출자를 모두 포함하며 취소와 오류 시에도 해제합니다. 이는 서버 전체 한도이며 유저별 인증 및 공정 배분은 아닙니다. 현재 공개 도구 입력에는 신뢰 가능한 사용자 신원이 없어 유저별 제한을 임의 질문 필드로 구현하지 않았습니다.

미적중 요청은 기존 검색 컨트롤러에서 병합하고 대기합니다. 실행 슬롯을 얻은 뒤 캐시를 다시 조회하여 대기 중 만들어진 결과를 재사용합니다. 캐시 적중에서는 전체 청크와 일정을 읽지 않습니다. 검색은 청크만, 일정은 일정만 읽으며 각 테이블의 최신 revision에 대한 JSON 디코딩 결과를 재사용합니다. 별도 프로세스가 데이터를 교체해도 SQLite 트랜잭션으로 revision을 확인하여 갱신합니다. 호출자에게 복사본을 제공해 메모리 스냅샷 변조를 막습니다. 이는 검색 인덱스 자체의 사전 계산이나 벡터 메모리 캐시는 아닙니다.

캐시 만료 정리와 축출에는 `expires` 인덱스를 사용합니다. 로그의 `cache_fast_path`는 검색 슬롯 우회 여부, `cache_lookup_ms`는 앞단 캐시 경로 대기와 실행을 합친 시간입니다. `coalesced`는 검색 작업 병합만 뜻하고 캐시 조회 병합은 포함하지 않습니다.

| 코드 | 의미 |
|---|---|
| `SERVER_BUSY` | 실행/대기열 용량 또는 호출자 한도 초과 |
| `QUEUE_TIMEOUT` | 실행 슬롯 대기 시간 초과 |
| `REQUEST_DEADLINE_EXCEEDED` | 전체 시간 예산 초과 |
| `DATA_CHANGED` | 처리 중 데이터 revision 변경 |
| `REQUEST_CANCELLED` | 모든 호출자가 떠난 작업 중단 |

MCP 도구 오류(`isError`)로 전달하며 `insufficient_evidence` 같은 업무 상태와 구분합니다. 서버는 자동 재시도하지 않습니다.

시간 예산에는 실행 슬롯 대기도 포함합니다. 검색과 모델 호출 전후, DB 트랜잭션 완료 전, 응답 반환 전에 만료를 확인합니다. 모델 API의 HTTP 타임아웃은 `min(기존 설정, 남은 시간)`으로 줄입니다.

동기 스레드나 이미 전송한 NPU 요청을 강제로 종료했다고 간주하지 않습니다. 호출자에게는 마감시간에 오류를 반환하지만 실제 작업이 끝날 때까지 실행 슬롯을 유지합니다. 작업이 돌아오면 다음 모델 호출과 캐시 저장을 막습니다. 원격 실행 취소는 현재 API 계약에 없어 지원하지 않습니다. 동기 작업의 체크포인트 사이 실행까지 즉시 중단하는 실시간 하드 마감 보장은 아닙니다.

## 적용 범위와 로그

MCP는 비동기 `asearch`/`acalendar`를 사용합니다. 동기 `search`/`calendar`는 내부 테스트와 오프라인용이며 입장 제어를 거치지 않습니다. 병합과 제한은 단일 프로세스, 단일 이벤트 루프 범위입니다. 여러 워커나 EC2에 걸친 전역 제어는 아닙니다.

로그에는 online/worker 범위, request ID, 지연, 대기 시간, 병합 여부, 모델 호출 수, 실행/대기 작업 수와 오류 코드가 기록됩니다. 질의와 대화 원문은 기록하지 않습니다.
